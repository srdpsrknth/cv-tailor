# CV Tailor product audit

Reviewed 2026-11-24 on `refactor/architecture-v2` at `2f784b2` using the Windows worktree, shared services, Streamlit tests, and a recent private output sample. This is a product audit and implementation proposal. [ASSESSMENT.md](ASSESSMENT.md) covers the underlying architecture. The audit keeps the current Streamlit design decision ([ADR 0020](DECISIONS/0020-streamlit-refactor.md)), explicit candidate scope ([ADR 0022](DECISIONS/0022-gui-profile-memory.md)), and the local private store ([ADR 0011](DECISIONS/0011-private-store-location.md)).

## Priority and acceptance

| Order | Change | Acceptance |
| --- | --- | --- |
| 1 | Put documents, editing and answers in a single application workspace | Select a recent application in one action. Download the CV PDF or open Answers in one more. Show results directly after generation. |
| 2 | Expand CV page-break options and add a layout preview | Compare frozen content against the current output. Preserve extraction, readability and two-page fit. Offer a preview before replacing a saved PDF. |
| 3 | Draft portal answers from saved application evidence | Paste a batch, draft explicitly, review every answer and copy each answer in one action. Save revisions by application and profile. |
| 4 | Pilot a private store on both computers | A Windows-generated application opens and downloads on macOS and a Mac-generated application does the reverse. Verify a conflict and restore with test data before migrating real data. |

The sync pilot can run alongside the GUI and layout work. It needs agreement on the two existing stores and coordinated access to both devices. The pilot does not depend on a hosted app.

## First implementation milestone

Use `refactor/architecture-v2` as the base. The first user-facing release opens a common application workspace after generation and from the recent-applications list. It offers the CV and cover-letter downloads near the application title. The lead owns the shared application lookup and integrates the other work as it passes its own checks.

| Agent | Owned area | First pull request or handoff |
| --- | --- | --- |
| GUI | `ui/app.py`, `ui/review.py`, and GUI tests | Direct workspace after generation, one-action recent application selection, and prominent downloads. Cover existing, failed and partial records. |
| CV layout | `backend/renderers/`, `templates/cv/`, and layout tests | Evaluate additional role and project break options with frozen content. Compare the same extracted text, page count and tail measurements. Return preview results to the lead for GUI integration. |
| Portal answers | New answer service, schemas and answer tests | Draft a batch against evidence from a saved application with a fake provider. Enforce limits and show missing facts. Keep model-backed research and GUI wiring for a follow-up. |
| Sync | Portability checks and synthetic pilot | Test a relocated store, incomplete replication, and conflict recovery. Run the two-device pilot when both computers are available. Coordinate any shared manifest change with the lead first. |

Before editing shared paths, agree on `profile_id` plus `job_id` as the workspace identity and how features read the saved posting, snapshot, and content revision. Prefer separate worktrees when Git metadata is writable. With restricted Git metadata, agents can work on disjoint paths in the existing development worktree and the lead can integrate and verify the combined changes. Keep the audit and project-state updates. The verification gate is a live GUI walkthrough, focused tests per workstream, and the full suite on a machine with working TeX. The real-data sync migration follows a successful synthetic round trip and restore.

## GUI and application workflow

| Task | Current workflow and cost | Proposed workflow |
| --- | --- | --- |
| Start from a job posting | Paste the full description. Company, role and country fields sit alongside a model selector and fresh-draft switch. A long URL can pass the current description-length check. | Accept a posting URL or pasted text in one entry area. Fetch only through supported sources, retain the original URL and provide paste fallback. Confirm inferred country when uncertain. Put model and fresh-draft choices under Advanced. |
| Generate and download | The result appears below the generation form. In Documents, setup and checking actions appear before download controls. The CV PDF, autofill DOCX and letter files are separate downloads. | Move directly into the application workspace. Put Download CV and Download letter next to the title, label the two document formats clearly, and offer a bundle as a secondary action. Keep checking tools beside the preview or under Details. |
| Resume a saved application | Open Applications, then open the selector and choose the entry. Search and filter controls occupy the top row. Entries on another page require pagination first. | Render a searchable recent-applications list with clickable rows that open the same workspace. Keep history filters available when needed. Persist an application address scoped to the active profile so a refresh can restore the view. |
| Revise a saved document | The shared documentation leads to `content.json` and a CLI render. The GUI exposes autofill regeneration and Word checking. | Add Edit text and Preview layout. Use the application snapshot by default and show a review diff if the user explicitly imports newer profile facts. Save text as a revision and render it without an LLM call. |
| Recover from an interrupted or failed run | Partial attempts can be reviewed. Starting another generation is easier to discover than recovering the existing text. | Show what was saved, what failed, and whether the next action has a model cost. Offer Render again when complete editable text survived, with the previous usable files still downloadable. |
| Discover a job | Connector search and posting handoff already work for supported sources. Portal URL intake is a separate gap. | Keep Find jobs. Send known posting text, country and source to the same intake. Clear or reconfirm source attribution if the user replaces the handoff text with a different posting. |

Use compact navigation, one visible active candidate label, and one primary action per screen. Start with a 16 px system sans text scale, a neutral canvas, one accent for actions, and visible keyboard focus. Use a short company and role header over **Documents**, **Answers**, and **Details**. Put the existing source comparison, model rationale and run history in Details. On narrow windows, keep the title and downloads above stacked content and avoid opening the PDFs inside a narrow nested scroll area. Verify at 1280 × 720 and at a 390 px viewport, including keyboard-only use. Treat the click targets in the table as acceptance criteria and repeat the common tasks against a running GUI.

`ui/review.py` requests PDF checks eagerly when opening an application. A timed local run over eight saved applications took 0.31–0.63 s per application for the review service with these checks. That excludes browser work. Make deeper checks lazy and reuse results by saved artifact and source fingerprint. Measure time to the download controls separately from preview completion. Keep validation, generation, store and rendering rules in the shared services so CLI and GUI continue to agree. Preserve the distinction between application generation state and real submission state. Phase 5 can own the latter if tracking is added.

## CV and cover letter

Nine recent application folders were examined. Eight contained a completed two-page CV and a one-page cover letter. One earlier attempt had only saved sources and recorded an undefined `layout` template variable. The later attempt for the same posting produced both PDFs. The eight successful CVs already had adaptive layout metadata and each fit in two pages on its first generation pass. The saved metadata records three to five layout trials per application. The cover letters had 296–308 body words.

| Observation | Sample evidence | Proposed change |
| --- | --- | --- |
| Large blank area before a clean break | Six CVs had 43–53 mm of unused printable height on page 1, often followed by a full employer block on page 2. | Generate additional bounded break options after a complete bullet or project group. Require visible employer and role context on a continuation. Attach a technology line to the matching role or final bullet group. |
| Page 2 starts with project headings | In two CVs the employer and role stayed on page 1 while two projects appeared on page 2. The continuation text carried the employer, but the handoff read more like a new section than the same role. | Use a compact employer/role continuation line and preserve proper grouping. Keep headings with their first complete bullet and penalize continuation when a comparably balanced clean break fits. |
| Page-balance warnings can miss the obvious cases | Every saved page occupied more than 75% of printable height. The layout warning threshold therefore missed the six visibly long page-one tails. | Show printable tail length and page-to-page gap in preview. Use 40 mm and a 12-point occupancy difference as initial advisory targets to tune against samples. Evaluate the largest tail as well as balance so two fairly empty pages do not look optimal. |
| Most blocks have similar visual weight | Small all-caps headings, repeated project labels, densely packed technology lines and long skill rows reduce scanning speed. Blue rules and the single-column body give a consistent structure. | Test one stronger hierarchy with shorter project labels, quieter dividers, and less compressed dates and skills. Keep 10.5 pt as the body minimum, use 11 pt when it fits, and preserve the single reading order in the PDF and the plain upload DOCX. |

The current template uses `samepage` around full employer bullet blocks and project blocks. The selector compares three typography presets and may try a break before one employer found through a split project. A clean two-page type setting can therefore win with a long white tail when the only alternative is three pages or a project split. Prefer trying additional break opportunities before changing copy or shrinking type. Score breaks from stable role and project identifiers and distinguish a role continuation, project continuation, orphan heading and split bullet. Keep structural integrity, both PDF extraction checks, and the two-page limit as gates. A balanced page remains a preference, since some content simply fills less space.

Use the eight frozen samples plus one-page, dense, long-headline and older synthetic fixtures. Compare preserved text and fields, reading order, used height, tail length, warning accuracy and render time. Review the actual PDFs at normal scale. Independently review the editable cover letter and autofill DOCX in both Word environments. The saved PDF review sampled 16 CV pages. Fresh TeX rendering, DOCX pagination and submission-portal extraction were outside the verified results of this run.

## Portal answers

Add **Answers** to every application plus an **Answers only** action at intake for applications that already have a CV. An answers-only record needs the saved posting and a selected profile. A missing PDF engine or cover letter should never block answer drafting. Preserve availability of editable answers when a provider or research service is unavailable.

1. Paste one or more exact questions. Split into editable rows with optional character or word limits. Let the user confirm the split for multiline portal text. Add short optional personal notes per question.
2. Build the candidate context from the saved profile snapshot and selected user-confirmed additions. Use the saved CV and cover letter for application emphasis, wording and consistency. They are derived drafts, so independently check their factual claims against the snapshot or user-confirmed notes. Treat current profile changes as opt-in and display material conflicts. Legacy applications can use an explicitly chosen current profile with visible missing-source states.
3. Use the saved job description for role responsibilities and employer claims from that posting. Offer **Research company** when company context would help. Submit the company, role and public URL to the search service where relevant. Keep candidate data, draft answers and private notes out of search queries. Prefer employer pages, date retrieved sources, and label uncertain claims. Keep public page text as quoted evidence in the drafting context. If research fails, surface the gap and allow a posting-based answer. Start with public URLs and manual source snippets, then add a configurable search connector when cost and coverage are understood.
4. Draft all selected questions with an explicit action. Reuse the provider abstraction, structured response parsing, task routing and usage tracking. Return answer text, evidence IDs, missing facts and limit status per question. A failed or invalid item should be retryable independently. No document generation should be necessary.
5. Display the application-ready answer in an editable field with a live character or word count and **Copy answer**. Keep source notes and unresolved facts beside it, outside the text that gets copied. Save explicit user edits and confirmed facts, preserve revisions and never infer approval from copying. Persist under the application folder using candidate-scoped IDs and atomic file replacement. Key reused drafts by question, limits, evidence, source revisions and prompt/model version.

| Question | Answer policy |
| --- | --- |
| Why this company or role? | Connect one concrete responsibility or company fact to one relevant experience or clearly expressed preference. Avoid claims about current strategy or team culture without a source. |
| What project are you proud of? | Use the candidate's selected project if available. Explain the situation, personal contribution, supported result and why it matters. Ask for the personal reason or result if the evidence is missing. Preserve whether the project is ongoing. |
| Tell us about a time you took initiative or used AI | Identify the action, reason and result. Keep the distinction between personally built, used and contributed to. Ask for a result if the source only documents the action. |
| Salary, availability, work authorization or yes/no | Show the specific known fact and ask the user to confirm or enter missing values. Keep these fields user-controlled. |

Evaluate with synthetic evidence fixtures covering multiple questions, tight limits, contradictory CV claims, missing outcomes, legacy records, irrelevant search and provider failure. Score specificity, voice, evidence coverage, ownership, duplication with the letter, and accurate counts. Include a review of the research request payload and tests that enforce candidate isolation.

## Windows and macOS sync

Use the existing private store layout with Syncthing and local rendering on both computers. The direct file approach fits this use case, including offline access on either machine. The Windows machine can be the seed and an always-on peer. Keep it separate from the existing emulator share. The Windows store has local Git history with no configured remote at audit time. Use Git for code and preserve private Git history independently. A private Git remote would add manual binary commits, pulls and merges. Clarify the distinction between checkout-local `outputs/` and the authoritative `<store>/outputs/` in [DEVELOPMENT.md](DEVELOPMENT.md) when the pilot is documented. The hosted store in [ADR 0006](DECISIONS/0006-remote-profile-access.md) is a future option for authentication, more devices or audited hosted access.

1. Inventory and back up each existing private store separately. Compare profiles and application folder IDs and reconcile differing files before enabling two-way sync. Keep device-specific `.env`, tools, GUI preferences, caches, logs, temp files and Git metadata local.
2. Pilot with dedicated folder shares for the store's `profiles/` and `outputs/` trees on both machines. Include source JSON, posting snapshots and app answers along with PDFs and DOCX files. Keep `applications/` as an optional separate archive share. Start from known copies with Windows as the seed. Point `CVTAILOR_STORE` on each machine to its own local store root. Choose a single authoritative output directory and keep `OUTPUTS_DIR` mirrors out of the sync set.
3. Validate a synthetic application and profile round trip in both directions and check file hashes. Simulate simultaneous edits, preserve both copies and verify restoration. Then move to send/receive with staggered file versioning on both peers and keep a separate backup. Syncthing handles conflicts per file and versions incoming revisions. An application with several files can still arrive in stages. [Synchronization and conflicts](https://docs.syncthing.net/users/syncing) · [Versioning](https://docs.syncthing.net/users/versioning.html) · [Folder modes](https://docs.syncthing.net/users/foldertypes.html)
4. Add a sync-portability pass before relying on concurrent work. Write relative artifact references in persisted metadata and resolve legacy files from the current job directory. Stage file writes and publish a manifest with expected files and hashes. When a folder is only partly replicated, serve the last coherent revision or show progress and retain usable files. Detect `.sync-conflict-*` files and stale revisions before saving over a profile or answer. Until then, finish syncing before editing the same profile or application on the other computer. Test both machines with matched application versions and comparable LaTeX packages and fonts.

The GUI review path already discovers files in the local job directory. In a synthetic relocation check, the application opened, its posting resolved, and its artifact downloaded successfully despite an invalid absolute artifact path in the manifest. Some persisted manifests still contain absolute artifact paths, and `application_store.write_json` writes directly to its target. Transporting complete folders is viable. Concurrent writes and partially replicated folders need explicit handling. The Windows Syncthing endpoint at the remembered port did not answer this session's health probe, and the Mac and its store were unavailable for verification. Deployment and real data transfer remain pending.
